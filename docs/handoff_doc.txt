CURRENT STATUS OF THE HUBS

Definition: A Hub is a Jupyter notebook that provides the computational framework for integrating, executing, and demonstrating additional functionalities that extend the capabilities of the CESM simulator model. Each of the functionalities are motivated in the grant proposal submitted from Jingyi’s lab for NSF described here https://uwmadison.box.com/s/2i0pffh5xc17yukzpqxztl4fru6n4rfx

Hub 1 - Data Analysis
Goal: providing the user this layer to explore the data from NEON (native data for CESM)
Input: The current development calls the data from S3. In S3 there is a copy of 3 NEON stations data, both input (NEON) and output (CESM output) of the CESM simulator for demonstration purposes.
Expected Output: Plots of data, histograms https://github.com/UW-Madison-DSI/exsoil-nsf-prototype-refactor/blob/main/notebooks/Data_Hub.ipynb
Status: Completed
Hub 2 - Modeling Hub
Goal: The hub ingests CESM output (native output after processing NEON data) and demonstrates the capabilities described in this framework for applying the Kalman Filter. Specifically, the hub evaluates model fit and performs parameter adjustments using a Kalman Filter–based approach.
Dependencies: https://github.com/UW-Madison-DSI/exsoil-nsf-prototype-refactor/tree/main/analytics_modules
Input: CESM simulations/outputs
Expected Output: https://github.com/UW-Madison-DSI/ctsm-nsf-demonstration/blob/main/notebooks/misfit_eval.ipynb
Status: Completed
Hub 3 - Experimentation Hub
Goal: The hub ingests NEON data into the CESM workflow, after specific scenarios of parameter perturbation or transformations. The hub is designed to demonstrate and compare how the CESM output when an input perturbation and when no perturbation of the input differ doing a t-test. This module touches the backend of CESM as it needs to process ”new” data e.g. NEON data under a transformation. It requires the output of CESM for data under perturbation and the output for data under no perturbation in order to generate 2 outputs to compare (please see diagram in page 4).
Dependencies: https://github.com/UW-Madison-DSI/exsoil-nsf-prototype-refactor/blob/main/cesm-tools/site_and_regional/run_neon_v2.py
Input: CESM simulations/outputs after transforming: PFT, Soil type and []
Expected Output: 
Status: Completed

Notes: 
Hub 2 has as a backend the framework here https://github.com/UW-Madison-DSI/exsoil-nsf-prototype-refactor/tree/main/analytics_modules
Hub 2 and 3 have not been tested against the new architecture/design that pulls native data from NEON
The rationale for incorporating S3 into the architecture is twofold: (1) it provides an immutable source of data that can be used as a reference for comparison after perturbations are introduced, and (2) it improves efficiency by reducing the need to repeatedly download data from NEON during the workflow.
No solution is inherently wrong; the new design reflects different considerations, preferences, and an evaluation of long-term maintenance and feasibility. Please view what I implemented as a resource that can be leveraged when useful, taking the aspects that provide the most value for the current and future needs.
