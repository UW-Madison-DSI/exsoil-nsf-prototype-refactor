Summary

The infrastructure phase is done: a multi-arch container runs standalone CTSM 5.4.043 and completes a NEON tower simulation end-to-end. We are now in the scientific-capability phase — getting the three analysis Hubs (Data Analysis, Modeling, Experimentation) running on live/native data across 5 NEON sites. This is a data-rebind and validation effort, not a redesign.

Planning is complete and tracked; the first execution phase (data contract) is done. This report is the shareable status snapshot.

What we completed this cycle (Phase 0)

  • Data contract — live CTSM output layout, streams, variables (TSOI, H2OSOI, GPP), dims, and units, grounded in the real KONZ run.
  • 5 sample sites confirmed: KONZ (baseline), ABBY, CPER, TALL, CLBJ.
  • Reference copies received and evaluated (343 MB, staged locally, gitignored):
    • Right sites, structure, and variables — plug into the existing reader with a path change.
    • Model output only — no NEON observations included.
    • Older model generation (legacy h1/h0, 2018-2022) — a shape/plausible-range oracle, not exact ground truth.
  • Naming discrepancy identified: live output uses h1a/h0a streams while the current code and reference copies use plain h1/h0. Phase 1 must handle both — catching this now avoids a silent failure.

Decisions pending (Jingyi)

  1. Observed-GPP source for Hub 2 (#12) — NEON API vs. evaluation_files vs. NCAR eval files. Blocks Phase 3 validation.
  2. ILAMB (#13) — accept the custom metrics, or build real ILAMB?
  3. EnKF (#14) — accept the simple Kalman filter, or build a true EnKF?
  4. Perturbation scope — precipitation-only for the MVP, with PFT/soil/temp as follow-ons?
  5. Validation tolerance — how close must live runs match the (older-model) reference copies to pass?

Next steps

  • Get decisions 1-3 in front of Jingyi — they set the scope of Hub 2 and whether any net-new work is needed.
